# ElastOS launcher

Status: the desktop app installs and supervises the ElastOS runtime only.

Founder decision on 2026-10-16: the previous computer app is gone from this repository. The launcher does not import its data. A runtime home starts empty. People who already have that install see Remove PC2. It lists the known paths and their sizes, and removes only those paths after a confirm.

| Decision | What this tree does |
|---|---|
| Product | The pinned ElastOS runtime. One Install button. |
| Update channel | `stable` is filled from runtime `main` when that head is published. `develop` maps to `canary` for testing. `"active"` in `resources/runtime-pin.json` is the switch. |
| Pin | Each launcher release pins a signed runtime version, UnixFS head CID, installer SHA-256, and maintainer DID. |
| Home | Fresh runtime data directory. No import of another product. |
| Windows | Dedicated WSL2 distro named `ElastOS`. |
| Intel Mac | “Intel Mac is not supported yet.” until a signed `darwin-x64` release exists. |
| Telemetry | None. |
| Signing | Hardened runtime, `resources/entitlements.mac.plist`, and `scripts/notarize.js`. Tag builds use the existing Apple secrets. |

## 1. How the launcher runs the runtime

The launcher is an Electron 28 shell. It does not embed the runtime. It downloads the pinned `install.sh`, checks the Ed25519 release head and the installer SHA-256, and runs:

`ELASTOS_HEAD_CID=<pin> bash install.sh --install-only --maintainer-did <did>`

The launcher drops every inherited `ELASTOS_*` variable before it starts install.sh, `elastos setup`, `elastos gateway`, or `elastos update` (`runtimeChildEnv` in `src/main/targets/releaseHead.ts`). install.sh lets `ELASTOS_MAINTAINER_DID`, `ELASTOS_PUBLISHER_GATEWAY`, `ELASTOS_PUBLISHER_NODE_ID`, `ELASTOS_SOURCE_CONNECT_TICKET`, `ELASTOS_IPNS_NAME`, and others replace its baked values, and the runtime reads many more. `ELASTOS_HEAD_CID` is then set from the signed pin. On Windows, wsl.exe gets no `ELASTOS_*` variable, and the distro command unsets each name install.sh reads (`INSTALLER_ENV_NAMES`) before it sets the head.

Install skips install.sh only when the installed version, the head CID in `sources.json`, and the signed install record (`installation/release-head.json`, verified against the pinned maintainer DID by `signedInstallRecord`, the check Reset uses) all match the pin (`planRuntimeInstall` in `src/main/targets/runtimeInstall.ts`). A missing, tampered, or foreign-signed record means ElastOS is not proven installed, so Install runs the pinned install.sh again. Its `install-release` step accepts the same version (it refuses only an older one) and writes only the binary, `sources.json`, and the two release files in `installation/` (runtime `update.rs` `install_release`, `install_transaction.rs` destinations). install.sh then runs `principal-root-upgrade`, as on every install, which keeps a rollback copy under `backups/`. Nothing else in the data folder is deleted. After install.sh, Install checks the record again and stops with a plain message if it is still not valid. This is what the Reset “Fix it” button relies on.

Before that command, the app puts its own `curl` and `sha256sum` on `PATH`, and a pinned CPython when this computer cannot run `python3 -c ''`. It does not ask for Xcode Command Line Tools. The click-by-click first run, including the Windows permission prompt and a possible restart, is `docs/FIRST_RUN.md`.

| Piece | File | Role |
|---|---|---|
| Main process | `src/main/index.ts` | Window, tray, and `elastos:*` IPC. It does not import `./targets`. |
| Supervisor | `src/main/launchController.ts` | Start, stop, install, update, reset, diagnostics. |
| Preload | `src/preload/index.ts` | `window.elastos`. |
| Renderer | `src/renderer/index.html`, `src/renderer/app.js`, `src/renderer/flow.js` | Install, then “Open my computer”. |
| Registry | `src/main/targets/` | One id, `runtime`. |

The tray says Start, Stop, and Open my computer. There is no Computer menu and no location dropdown.

The Home address lives in one file, `src/main/targets/gatewayAddress.ts`: the launcher starts `elastos gateway --addr localhost:8090` and opens `http://localhost:8090/home/`. Browsers refuse a passkey on an IP-literal origin such as `127.0.0.1`. `localhost` can resolve to `127.0.0.1`, `::1`, or both, and the browser can connect to any of them, so `probeGatewayHealth` (`src/main/targets/runtimeGateway.ts`) asks `/healthz` on every address `localhost` resolves to, with `Host: localhost:8090`. A resolver that names any other address is refused, and preflight blocks Install with a plain message. An address that answers without `OK` makes the result not OK. On Linux and macOS an `OK` counts only when the started gateway pid owns every listening socket on port 8090 for `127.0.0.1` and `::1` (`/proc/net/tcp` and `/proc/net/tcp6` on Linux, `lsof` on macOS) and owns every address that answered. A socket of another process on either address, or on a wildcard that covers one, is refused. Preflight treats port 8090 as busy when either `127.0.0.1` or `::1` is taken; a computer without IPv6 checks `127.0.0.1` only.

A gateway an earlier launcher started records `127.0.0.1:8090` in its host lock. When the identity check proves it is the installed gateway, Start stops it once and starts it again on `localhost:8090`. Reset and Uninstall can stop it too. Home is never opened on it. Any other lock address is not adopted.

On Windows the gateway runs inside the distro and Windows forwards `localhost` to it. Inside the distro the lock pid must own every gateway socket in `/proc/net/tcp` and `/proc/net/tcp6`. On the Windows side the launcher probes each address Windows resolves `localhost` to (usually `::1` and `127.0.0.1`) and accepts whichever family the forward serves; the Windows browser tries both. Gap: the launcher cannot tell which Windows process owns the Windows end of `localhost:8090`, so a Windows program on that port is caught only when it answers without `OK`.

## 2. Paths

| | Runtime |
|---|---|
| Program | `~/.local/bin/elastos` |
| Data | `~/Library/Application Support/elastos` on macOS, otherwise `$XDG_DATA_HOME/elastos` or `~/.local/share/elastos` |
| Lock | `{data}/host-process.lock` |
| Stage | `~/.elastos-launcher/install-stage.json` |
| Health | `GET http://localhost:8090/healthz` body `OK` |
| Home | `http://localhost:8090/home/` |

Reset and uninstall remove a path only when it is an exact default for this account (`os.homedir()`): `~/.local/bin/elastos`, `~/.local/share/elastos` (macOS `~/Library/Application Support/elastos`) and its `host-process.lock`, `~/.elastos-launcher/install-stage.json`, and `~/.elastos-launcher/resume-install.json`. Reset also removes `~/.elastos-launcher/resume-install.json.lock`. The support bundle is `Desktop/ElastOS-support.txt` or `ElastOS-support.txt` in that same home. `$XDG_DATA_HOME/elastos` under this home is removed when the directory is empty or holds only `components.json`, `host-process.lock`, and `sources.json` as regular files. It is also removed when every entry has a name the runtime writes (`RUNTIME_DATA_NAMES` in `src/main/targets/runtimePaths.ts`) and `installation/release-head.json`, which install.sh saves, verifies against the pinned maintainer DID. A host lock, a components manifest, or a filename alone is not proof. Any other entry, including a user file beside that record, a symlink, or a publisher's `release-key.hex`, is refused by name. The default `~/.local/share/elastos` stays on the list when `XDG_DATA_HOME` points somewhere else. Reset removes the data directory from that variable, so a path outside the home is refused. On Windows, removal compares the real path and the file index and does not open a directory. The last delete is still the holding path. A relative XDG path, a `..` segment, another account, a data directory outside the home, and a bare `<dir>/elastos` under the home are refused. A home with spaces or non-English characters is accepted when it is this account's home. `ELASTOS_LAUNCH_TARGET=pc2` opens the runtime and logs that PC2 is retired. Any other name is refused.

Reset first offers a copy of the data folder (`src/main/targets/runtimeBackup.ts`). The dialog shows the size, the folder, and that the copy holds keys and the sign-in identity. Reset stays off until the person picks “Save a copy of your ElastOS data first” or “Do not save a copy”, and the main process refuses a Reset request without one of those two answers. The copy is a zip named `ElastOS-data-<date>-<time>Z.zip` (mode 0600) in `~/ElastOS-backups` (mode 0700, a real folder of this account). A name that exists is never replaced; the next copy in the same second gets `-2`, `-3`, and so on. It leaves out what Install writes again: install.sh's release files (`bin`, `capsules` with downloaded models, `libexec`, `tools`, `scripts`, `browser-vm/image-set`, `model-catalog.json`, `components.json`, `sources.json`, `installation`, `update-controller`), VM images and sockets, caches, `model-preparation`, and the lock and coords files (`RUNTIME_BACKUP_EXCLUDES`). Every other name is kept. Free space is checked before the gateway stops and again before the copy; too little space refuses Reset with the sizes. The copy runs after Stop and before any delete. If it fails, nothing is deleted and the message says so. The zip does not keep file modes, so restored keys need their modes set again. Gap: on Windows the data is inside the ElastOS distro, and Reset does not delete that folder, so there is nothing to copy; Reset on Windows removes only launcher files on the Windows side.

Uninstall on Windows removes the whole ElastOS WSL2 Linux environment with `wsl.exe --unregister ElastOS` (`src/main/targets/windowsUninstall.ts`). Before it stops anything, it runs the Reset checks with the same code (`windowsReset.ts`): python3 in the distro, the data-folder ownership rule, no other drive or mount, and the signed install record (a partial install or a missing record is refused, and Fix it runs Install, which writes the record). It checks the free space for a copy of the whole environment, and offers the same copy of the data folder as Reset. After Stop and that copy, the main process asks a second question in a Windows dialog (Cancel is the default). Only after a yes, in this order: `wsl.exe --list --quiet` again, decoded as UTF-16LE (or UTF-8) and read by line, must have exactly one line that is exactly `ElastOS` and no other case of that name; the ownership rule and the same install record are checked again; `wsl.exe --terminate ElastOS`, then `wsl.exe --export ElastOS <file>` saves the whole environment as `ElastOS-linux-<date>-<time>Z.tar` in the same owner-only `%USERPROFILE%\ElastOS-backups` folder (a name that exists is never replaced; the file must be a complete tar file and then gets owner-only access); the list is read again; `wsl.exe --unregister ElastOS` runs once; and the list must no longer have `ElastOS`. A failed or incomplete export, too little space, a no, a changed list or record, or a wsl.exe error removes nothing, and a part file is deleted. Every wsl.exe call is `execFile` with a fixed argument list and no shell. The saved file holds everything in the environment, also files outside the data folder; the window says where it is and how to bring it back: `wsl --import ElastOS C:\ElastOS\distro "<file>"`. On macOS and Linux, Uninstall is unchanged.

Remove PC2 is a separate action in `src/main/legacyPc2Removal.ts`. The button stays hidden until a legacy install is on disk: `~/.pc2`, `~/.elastos/node` when it is the old bundled Node 22.13.1 tree, a PC2 launch agent or autostart file, a sudoers file whose text matches the rules the old installer wrote (`/etc/sudoers.d/wireguard` with `wg-quick`, or `/etc/sudoers.d/amneziawg` with `NOPASSWD:SETENV`, `amneziawg-go`, and `/var/run/amneziawg/`) together with one of those installs, a `~/.pc2` folder inside another Windows Linux distro, or a Windows distro named `pc2` or `pc2-wsl` that itself contains that folder or Node tree. The old installer never wrote `/etc/sudoers.d/elastos` or `/etc/sudoers.d/pc2-wireguard`. This repo has no hash for the VPN programs it compiled, so those programs are not deleted by name. The ElastOS distro is never unregistered. The confirm dialog lists each path and its size. Removal deletes only the paths from that list. “Back up my PC2 data first” must write a backup before anything is deleted, including a Windows Linux folder or distro; if that backup cannot be saved, nothing is removed. One privileged prompt covers a matching sudoers rule. That prompt is pkexec. Cancelling it (exit 126), a missing authorization or a missing prompt (exit 127), and a missing pkexec program each have their own sentence. pkexec is not replaced with sudo. An exit after the prompt has started is the removal command's own result. The list of files still there is what that privileged script can see, including a sudoers file the app itself cannot stat. A failure says what is still there and saves a support bundle.

Stop signals the gateway process group: `SIGTERM`, 15 seconds, then `SIGKILL`, after the pid has exited and `/healthz` has failed twice. Quit shows Stopping and waits long enough for both of those waits and their health probes. If that wait expires, Quit sends `SIGKILL` only to a gateway this window started, and then closes the window. Quit, Stop, and Restart leave a gateway this window did not start running. Reset and Uninstall, after the confirm dialog, adopt that gateway from the host lock and signal the pid they read. They do not ask again. On Windows they adopt only when the distro facts say the listener is ElastOS. A different listener, and a facts read that fails, is left running. On macOS and Linux the adopt itself checks the host lock, the command line, and the health socket. On Windows, an error asking whether that pid has exited is treated as still running. Exit 75 restarts only when the binary was replaced on disk.

The support bundle redacts labeled secrets (`password`, `token`, `api_key`, `attach_secret`, `cookie`, `authorization`, `seed`, `mnemonic`, `private_key`, `secret`, bearer tokens, and JWTs), the rest of a `seed`, `mnemonic`, `private_key`, or `secret` line, a run of 12 or more BIP39 words in any case, split by spaces, line breaks, commas, hyphens, quotes, or numbering such as `1.` or `2:`, known secret prefixes (AWS access key ids, `ghp_` tokens, and `sk-` keys), hex of 32 or more characters with or without `0x`, including a 64-character hex string unless that line is labelled sha256 or hash, hex wrapped over two or more lines that holds 32 or more characters together (a list of whole 40- or 64-character hashes stays), an unlabeled uppercase token of 16 or more characters that contains a digit and no underscore, a lowercase token of 32 or more characters with high entropy, and an unlabeled mixed-case token of 20 or more characters with high entropy. It keeps paths, a 40-character hex hash on its own line or beside a hash, cid, commit, or installer label, a 64-character hex string on a sha256 or hash line, CIDv0 and CIDv1, `did:key` values, versions, UUIDs, and `UPPER_SNAKE` names. An unlabeled secret shorter than that, or with low entropy, is not redacted. `secret-line` is a short phrase that stays.

When the window is shown again, earlier runtime log lines are sent to that window only. They are not written back into the launcher log file.

On Windows the same installer runs inside distro `ElastOS` as root, and the Windows process reads `/healthz` on each address Windows resolves `localhost` to. If turning on Linux support asks for a restart, the next open continues Install when Linux support is on and ElastOS is not already installed. The resume file stays until that Install succeeds. Reset removes it and `resume-install.json.lock`. If Linux support is still off, or Windows cannot be checked, Install waits. A second open does not start a second Install while the first process is still alive and refreshing the lock. The holder refreshes the lock's timestamp. A lock that has not been refreshed for two minutes, an empty lock, a dead pid, or a lock from before the last boot can be claimed again. On Linux a pid whose start time changed is also stale; Windows has no start time, so a reused pid there waits out the two minutes. One reclaim token (`resume-install.json.lock.reclaim`) lets one open at a time reclaim. A token whose holder is dead, from before the last boot, or older than 30 seconds can be taken; a racer that moves a live token puts it back and stops. Reclaim does not replace a lock another process created while the stale bytes were set aside, and an open that finishes removes only its own lock. Without a token left by a crash, any number of opens reclaim one at a time. After a crash inside a reclaim, two opens at once still give one claim; a third open that lands in the few milliseconds of a token put-back can still give a second claim.
